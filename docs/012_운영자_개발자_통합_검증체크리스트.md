# 012 운영자·개발자 통합 검증 체크리스트

## 목적
이 문서는 관리자 기능 확장(005~011)을 실제 운영에 반영할 때, 운영자와 개발자가 같은 순서로 점검하도록 만든 단일 실행 문서다.

운영 장애의 상당수는 “기능 버그”가 아니라 “점검 순서 불일치”에서 발생한다. 운영자는 화면에서 이상을 보고, 개발자는 코드만 확인하다가 배포/환경 문제를 놓치는 경우가 많다. 이 체크리스트는 역할이 다른 두 주체가 동일한 관찰 지점을 순서대로 확인하도록 설계되었다.

즉, 이 문서의 목표는 단순 확인 항목 나열이 아니라, 누구나 같은 절차를 따라 같은 결론에 도달하게 만드는 것이다. 팀원이 바뀌어도 동일한 품질로 배포/검증을 재현할 수 있어야 장기 운영이 가능하다.

---

## A. 배포 전 체크(Pre-flight)
| 점검 항목 | 운영자 | 개발자 | 완료 기준 |
|---|---|---|---|
| 시즌 시트명 규칙 | `season_nn` 확인 | 시즌 파싱 정규식 확인 | 시트/URL/관리자 표시 일치 |
| variable 스키마 | A:I 헤더 확인 | `variablesGet` 응답 확인 | `key~used_in` 9컬럼 유지 |
| 필수 변수 10개 | 값 채움 확인 | 템플릿 기본값 확인 | 누락 키 0건 |
| Apps Script 배포 URL | 최신 `.../exec` 확보 | `apiInfo` 응답 확인 | 최신 `apiVersion` 조회 가능 |
| GitHub Secret | `APPS_SCRIPT_WEB_APP_URL` 갱신 | workflow 입력값 확인 | Secret 비어있지 않음 |

Pre-flight 단계는 “실제 배포 전에 실패할 조건을 제거”하는 구간이다. 여기서 누락이 있으면 배포 이후 증상이 기능 장애처럼 퍼지므로, 시간이 급해도 생략하지 않는 것이 원칙이다.

## B. 배포 체크(Release)
| 순서 | 작업 | 성공 기준 |
|---|---|---|
| 1 | Apps Script 새 버전 배포 | 최신 버전 번호/URL 확인 |
| 2 | GitHub Secret 갱신 | 저장 완료 |
| 3 | GitHub Pages workflow 실행 | Action 성공, 배포 URL 갱신 |
| 4 | 관리자/학생 강력 새로고침 | 콘솔 에러 없음 |

Release 단계는 완료 여부를 선언하는 단계가 아니라, “배포 산출물이 실제 서비스에 반영됐는지”를 확인하는 단계다. 특히 캐시로 인해 구버전 화면이 보이는 상황이 반복되므로 강력 새로고침을 체크 항목으로 고정했다.

## C. 배포 후 기능 체크(E2E)
| 기능 | 테스트 절차 | 기대 결과 |
|---|---|---|
| 시즌 전환 | 상단 참조 시트 변경 후 탭 조회 | 선택 시즌 데이터만 표시 |
| 시트 바로가기 | `Google Sheets 바로가기` 클릭 | 정확한 시즌 탭(gid) 이동 |
| 출석 카운트다운 | 오픈 전/후 상태 확인 | 문구/잔여시간 정상 |
| 랭킹 정렬 | 6/6 vs 4/4 데이터 비교 | 6/6이 우선 |
| 일정 캘린더 | 같은 날짜 신규 저장 시도 | `SCHEDULE_DATE_DUPLICATE` 차단 |
| 변수 저장 | `value` 변경 저장 | 계산 즉시 반영 |
| 유고 2중확인 | 출석 셀 유고 덮어쓰기 | 2단계 확인 후 반영 |
| 수료 판정 | 변수 변경 후 보고서 재조회 | 판정 결과 재계산 |

E2E 단계는 기능 간 연쇄 영향을 확인하는 단계다. 예를 들어 변수 변경은 변수 탭에서 끝나는 작업이 아니라, 출석·유고·수료 계산까지 모두 영향을 미친다. 따라서 탭별 단건 확인보다 “연결된 흐름” 검증이 중요하다.

## D. 장애 우선순위 대응
| 우선순위 | 증상 | 1차 확인 | 2차 조치 |
|---|---|---|---|
| P1 | API_BASE_URL 미설정 | `env.js` URL 주입 확인 | Secret 재검증 + Pages 재배포 |
| P1 | variable 중복 증가 | `variablesGet` 버전/지원액션 확인 | `variablesNormalize` 실행 |
| P2 | 유고 덮어쓰기 무검증 | `excusedSet` 에러코드 확인 | 백엔드 재배포 + 프런트 캐시 갱신 |
| P2 | 일정 중복 저장 | `scheduleSave` 에러코드 확인 | 충돌 회차 정리 후 저장 |
| P3 | 메타가 `-` 표기 | 시트 `applies_*` 값 확인 | 템플릿 복구(value 유지) |

우선순위 표는 체감 불편보다 운영 영향도를 기준으로 정렬했다. 예를 들어 메타 표기 문제는 중요하지만, API URL 미설정처럼 시스템 전체를 멈추게 하지는 않는다. 이 기준을 고정해두면 긴급 상황에서 복구 순서가 흔들리지 않는다.

## E. 실제 운영 사례 리허설(실패 예시/대응 예시)
### 사례 1. 배포 후 변수 탭에서 `미정(템플릿 복구 필요)`가 대량 표기된 경우
실패 상황: 배포 직후 변수 목록의 적용 위치/시점이 대부분 비어 보여 운영자가 “배포 실패”로 판단했다.  
원인: 변수 메타가 누락된 중복행이 남아 있었고, 구버전 캐시가 일부 응답 필드(camel/snake)를 혼합 노출했다.  
대응: `apiInfo`로 백엔드 버전을 확인한 뒤 `variablesNormalize`를 실행하고, 템플릿 복구(value 유지)를 1회 적용했다. 이후 강력 새로고침으로 메타 렌더를 재확인했다.  
재발 방지: 배포 후 첫 점검을 항상 `A -> B -> D(P1/P2)` 순서로 수행해, UI 체감 이슈를 바로 기능 결함으로 단정하지 않도록 운영 규칙을 명시했다.

### 사례 2. 일정 캘린더 추가 후 수료 판정 수치가 갑자기 달라진 경우
실패 상황: 일정 저장은 정상처럼 보였지만 수료표의 결석 환산 결과가 예상과 다르게 바뀌었다.  
원인: 같은 날짜 중복 회차가 과거 데이터에 남아 있어 출석 모수 계산이 달라졌다.  
대응: `scheduleList.dateConflicts`를 확인해 충돌 회차를 정리한 뒤, 수료 보고서를 재생성했다. 동시에 `variable`의 수료 기준값이 의도한 값인지 재확인했다.  
재발 방지: 일정 수정 작업을 한 날에는 E2E의 `일정 캘린더 -> 변수 저장 -> 수료 판정` 3연속 검증을 필수 절차로 고정했다.

## API/인터페이스 문서화 표 (운영 기준)
| API 액션 | 목적 | 핵심 요청 파라미터 | 핵심 응답 필드 | 관련 문서 |
|---|---|---|---|---|
| `sheetLink` | 현재 시즌 시트 링크 조회 | `season`, `adminToken` | `url`, `gid`, `sheetName` | 006 |
| `variablesGet` | 변수 조회(읽기 전용) | `adminToken` | `items[]`, `usedTabsText`, `appliesTo`, `appliesWhen` | 007 |
| `variablesUpdate` | 변수 값 저장 | `adminToken`, `items[{key,value}]` | `updatedCount`, `updatedAt` | 007 |
| `variablesNormalize` | 변수 중복/오염 정리 | `adminToken` | `duplicateRemovedCount`, `invalidValueDroppedCount`, `filledByDefaultCount` | 007 |
| `variablesResetTemplate` | 템플릿 복구/초기화 | `adminToken`, `mode` | `mode`, `resetCount` | 007 |
| `scheduleList` | 시즌 일정 조회 | `season`, `adminToken` | `items[]`, `dateKey`, `startHhmm`, `dateConflicts` | 009 |
| `scheduleSave` | 일정 저장/수정 | `season`, `sessionKey`, `startAt`, `endAt`, `adminToken` | `saved`, `sessionKey`, 오류 시 `SCHEDULE_DATE_DUPLICATE` | 009 |
| `scheduleDelete` | 일정 삭제 | `season`, `sessionKey`, `adminToken`, `force` | `deleted`, `requiresForce` | 009 |
| `manualApprove` | 관리자 수동 출석 승인 | `season`, `sessionKey`, `phone`, `adminToken` | `approved`, `recordedAt` | 008 |
| `excusedSet` | 유고 지정/해제 | `season`, `sessionKey`, `phone`, `comment`, `forceOverride`, `previewOnly`, `adminToken` | `updated`, `requiresOverride`, `existingStatus` | 008 |
| `graduationReport` | 수료 판정 데이터 조회 | `season`, `adminToken` | `rows[]`, `variables`, `rules` | 008 |
| `apiInfo` | 백엔드 버전/지원 액션 확인 | 없음(또는 `season`) | `apiVersion`, `supportedActions`, `serverTime`, `scriptTimeZone` | 011 |

## 운영자 실행 메모
1. 기능 점검은 `시즌 선택 -> 일정/변수 -> 출석/유고 -> 수료` 순서로 진행한다.
2. 배포 직후 오류가 나면 기능 코드보다 먼저 URL/버전 불일치를 의심한다.
3. `variable`은 반드시 1키 1행 원칙을 유지하고, 수동 복붙보다 관리자 UI 저장을 우선 사용한다.

## 개발자 실행 메모
1. 조회 API(`variablesGet`)와 수정 API(`variablesUpdate`)의 write side-effect 분리를 지킨다.
2. 신규 기능 추가 시 문서 005~012 중 최소 1개 이상을 업데이트해 운영 근거를 남긴다.
3. 커밋 메시지에는 기능 배경과 운영 영향(무엇이 바뀌는지)을 같이 기록한다.
