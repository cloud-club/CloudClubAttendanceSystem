# 013 시즌업데이트 운영한계 및 임시 운영정책

## 1. 배경(어떤 이유로 추가됐는지)
시즌 업로드 기능은 `생성(create)` 경로와 `업데이트(update)` 경로를 함께 제공하지만, 실제 운영에서는 업데이트 경로에서 다음 이슈가 반복적으로 관찰되었다.

- 미리보기에서 다수 행/셀이 `DELETE_CANDIDATE` 중심으로 과대 표기되는 체감 문제
- 입력 파일 형태가 시즌 시트의 정규화 형태와 다를 때(전화번호/이메일/공백/헤더 변형) Diff가 과민하게 반응하는 문제
- 특정 파일에서 `INF_REQUIRED_LOW_CONF_PHONE`, `INF_REQUIRED_LOW_CONF_EMAIL`, `INF_NO_VALID_ROWS`가 함께 발생하며 반영 자체가 차단되는 문제

핵심은 “업데이트 로직이 완전히 무의미하다”가 아니라, **동일 데이터라도 표현 형태가 다르면 현재 비교 기준에서 다른 데이터로 읽힐 수 있다**는 점이다.  
따라서 단기 운영에서는 업데이트 사용 범위를 제한하고, 생성 경로를 우선 경로로 고정하는 정책이 필요하다.

## 2. 사용자 절차(어떻게 사용하는지)
### 2-1. 기본 운영 원칙 (당분간)
1. 신규 시즌/대량 반영은 `생성(create)` 경로를 기본으로 사용한다.
2. 업데이트 모드는 “파일 형태가 기존 운영 템플릿과 거의 동일한 경우”에만 제한적으로 사용한다.
3. 업데이트 미리보기에서 `DELETE_CANDIDATE`가 과도하게 보이면 즉시 중단하고 `create` 우회 경로를 선택한다.

### 2-2. 업데이트 모드 사용 허용 조건
1. 전화번호/이메일 필드가 자동 추론 또는 수동 매핑으로 안정적으로 고정되어야 한다.
2. 디버그에서 `INF_REQUIRED_LOW_CONF_*` 계열 BLOCKER가 없어야 한다.
3. 유효 행이 충분히 확보되어야 한다(`INF_NO_VALID_ROWS` 금지).
4. Diff 미리보기에서 변경 의도와 실제 표시가 일치하는지 운영자가 수동으로 확인한다.

### 2-3. 즉시 우회 기준
- `DELETE_CANDIDATE`가 과도하게 발생해 검증 비용이 높아진 경우
- 전화번호 형식 경고가 연속 발생해 유효 행이 사실상 사라지는 경우
- 매핑 확정 후에도 필수 신뢰도 BLOCKER가 해소되지 않는 경우

위 조건 중 하나라도 충족되면 업데이트 시도를 종료하고 `create` 중심 운영으로 전환한다.

## 3. 설계 의도(왜 이렇게 했는지)
운영 문서의 목적은 “업데이트 기능을 무조건 쓰게 하는 것”이 아니라, **장애 비용이 낮은 경로를 표준화**하는 것이다.

- 단기 목표: 운영 안정성 확보 (`create` 경로 신뢰도 유지)
- 중기 목표: 업데이트 경로의 비교 정확도·설명 가능성 개선
- 장기 목표: 기존 전체시트 기반 Diff 업데이트를 운영 가능한 수준으로 고도화

즉, 이번 정책은 후퇴가 아니라 위험 통제다. 기능을 폐기하지 않고, 신뢰 수준에 맞춰 사용 범위를 조정하는 보수적 운영 전략이다.

## 6. 운영상 주의점
- 업데이트 모드에서 “변경이 많아 보이는 것”과 “실제 데이터가 많이 바뀐 것”은 다를 수 있다.
- 동일 의미 데이터라도 표현 형식(하이픈/공백/대소문자/도메인 정규화)에 따라 현재 Diff 결과가 달라질 수 있다.
- `INF_REQUIRED_LOW_CONF_*` BLOCKER는 UI 문제보다 입력 파일 구조 문제일 가능성이 높다.
- 업데이트 실패 시에는 기능 자체를 반복 시도하기보다 파일 정규화 또는 create 우회 여부를 먼저 판단한다.

## 7. 검증 시나리오
1. 동일 템플릿 파일로 update를 수행했을 때 Diff가 최소 변경만 표시되는지 확인한다.
2. 전화번호 형식이 섞인 파일(하이픈/문자 포함)을 넣었을 때 BLOCKER 발생과 안내 문구가 예상대로 나오는지 확인한다.
3. `DELETE_CANDIDATE` 과다 표시 상황에서 운영자가 create 우회 정책으로 전환할 수 있는지 확인한다.
4. active 세션 잔존 후 재시도 시 자동 복구/중단 흐름이 동작하는지 확인한다.

## 8. 실제 운영 사례(실패 예시/대응 예시)
### 사례 1. 변경이 일부인데 DELETE_CANDIDATE가 대량 노출된 경우
실패 상황: 운영자가 보기엔 일부 컬럼만 수정했는데 미리보기는 삭제 후보가 과도하게 보였다.  
원인: 업로드 원본과 시즌 시트의 표현 형태가 다르고, 현재 비교 규칙은 표현 차이를 보수적으로 변경으로 간주한다.  
대응: 업데이트 반영을 중단하고 생성 경로 우선 운영 정책으로 전환했다.  
재발 방지: 파일 표준화 체크(전화번호/이메일/헤더) 선행 후 업데이트를 제한적으로 사용한다.

### 사례 2. 필수 신뢰도 BLOCKER와 전화번호 경고가 동시에 발생한 경우
실패 상황: `INF_REQUIRED_LOW_CONF_PHONE/EMAIL`, `INF_NO_VALID_ROWS`로 반영이 차단되었다.  
원인: 필수 컬럼 자동 추론 실패 + 전화번호 형식 불일치로 유효 행이 사라졌다.  
대응: 수동 매핑 확정 후에도 실패하면 해당 파일은 업데이트 대상에서 제외하고 표준 템플릿으로 재정리했다.  
재발 방지: 업로드 전 표준화 런북(`014`)에 따라 사전 정규화를 의무화한다.

## 9. 남은 리스크/차기 개선 포인트
- 현재 운영 정책은 안정성을 위해 업데이트 범위를 제한하므로, 대규모 기존 시즌 변경 작업의 자동화 이점이 작다.
- 향후에는 **기존 전체시트 Diff 기반 업데이트**를 목표로 정규화 규칙/동등성 판단/오탐 억제 로직을 별도 단계로 고도화해야 한다.
- 차기 개선 방향과 단계별 설계는 `015` 문서에서 관리한다.
