# 004 세션 리다이렉트 ORB 이슈 해결 기록

## 문서 목적

이 문서는 마이그레이션 이후 발생한 세션 관련 장애를 "증상 -> 재현 -> 원인 확정 -> 수정 -> 검증" 순서로 설명합니다. 단순히 무엇을 고쳤는지보다, 왜 그 수정이 필요했고 어떤 근거로 결론을 냈는지를 기록하는 데 집중합니다.

---

## 1. 장애가 어떻게 보였는가

운영자가 처음 체감한 증상은 두 가지였습니다. 관리자 페이지에서는 비밀번호를 입력해도 로그인이 완료되지 않고 "네트워크 오류"가 반복되었고, 학생 페이지에서는 시즌 URL로 접속해도 세션과 랭킹 데이터를 불러오지 못했습니다.

표면적으로는 서로 다른 화면에서 발생한 문제처럼 보였지만, 네트워크 로그를 보면 둘 다 공통 통신 계층에서 실패하고 있었습니다. 즉, 관리자 기능 문제도 아니고 학생 기능 문제도 아니라, 두 화면이 같이 쓰는 JSONP 요청 경로가 핵심 이슈였습니다.

---

## 2. 재현 과정에서 확인한 사실

HAR를 분석했을 때 반복적으로 동일한 체인이 관찰되었습니다.

1. `script.google.com/macros/s/.../exec` 요청이 발생한다.
2. 서버가 `/macros/u/2/s/...` 경로로 302 리다이렉트한다.
3. 리다이렉트된 응답이 JavaScript가 아니라 HTML 404로 돌아온다.
4. 브라우저가 ORB(`ERR_BLOCKED_BY_ORB`)로 스크립트 로드를 차단한다.

결국 프런트에서는 `script.onerror`가 발생하고, 사용자에게는 모두 "네트워크 오류"로만 보이게 됩니다.

---

## 3. 원인 분석

이 문제의 본질은 "요청이 계정 컨텍스트에 영향을 받는다"는 점이었습니다. 다중 Google 계정 로그인 환경에서 요청이 `/u/{n}` 경로로 이동하면, 특정 조건에서 스크립트 응답 대신 HTML 에러 페이지를 받게 됩니다. JSONP는 응답이 반드시 JavaScript여야 하므로, 이 순간 브라우저가 로드를 차단하고 요청이 실패합니다.

즉, 원인은 출석 로직이나 시트 로직이 아니라 "브라우저가 스크립트를 가져오는 방식"에 있었습니다.

---

## 4. 의사결정 흐름 (질의응답 요약)

이번 대응에서 중요한 판단은 다음과 같았습니다.

첫째, 관리자와 학생 화면을 따로 고치지 않고 공통 모듈(`web/shared/api-jsonp.js`)을 먼저 수정하기로 했습니다. 두 화면이 같은 실패 패턴을 보였기 때문입니다.

둘째, API 스펙은 유지하고 전송 정책만 조정하기로 했습니다. 서버 인터페이스를 흔들면 회귀 범위가 넓어지므로, 먼저 로더 속성 변경으로 리다이렉트 영향을 줄이는 방향이 안전하다고 판단했습니다.

셋째, 재발 시 추적이 가능하도록 오류 메시지와 디버그 정보를 강화했습니다. 사용자 안내 문구는 행동 가능하게 바꾸고, 운영자 로그에는 민감값 마스킹된 진단 정보를 남기기로 했습니다.

---

## 5. 실제 수정 내용

### 5-1. `web/shared/api-jsonp.js`

가장 중요한 수정은 script 태그 생성 시 아래 속성을 명시한 것입니다.

- `crossOrigin = 'anonymous'`
- `referrerPolicy = 'no-referrer'`

이 설정으로 계정 컨텍스트 의존 리다이렉트 영향을 줄이고, script 로딩 경로를 더 안정적으로 만들었습니다.

동시에 `API_TIMEOUT_MS` 설정 연동을 추가해 통신 타임아웃을 운영 환경에서 조정할 수 있게 했고, 오류 객체에 `action`과 `debugUrl`을 포함해 디버깅 정보를 강화했습니다. 이때 `adminKey`, `adminToken`, `phone`은 `REDACTED` 처리해 민감정보가 콘솔에 노출되지 않도록 했습니다.

### 5-2. `web/shared/config.js` / `config.example.js`

통신 관련 기본값(`JSONP_CROSSORIGIN`, `JSONP_REFERRER_POLICY`, `API_TIMEOUT_MS`)을 설정 파일로 끌어올려 환경별 오버라이드가 가능하도록 만들었습니다.

### 5-3. `web/admin/admin.js`, `web/student/student.js`

`NETWORK_ERROR`를 단순한 문구로 숨기지 않고, "리다이렉트/ORB 가능성"을 안내하도록 메시지를 개선했습니다. 기능 동작 자체는 유지하면서 사용자/운영자 모두가 원인 방향을 더 빨리 파악할 수 있게 바꾼 것입니다.

### 5-4. 반영 커밋

이 변경은 커밋 `cdfa27b`에 반영되었습니다.

## 6. 검증 결과

수정 후에는 네트워크 흐름에서 `script.google.com -> script.googleusercontent -> 200 text/javascript` 패턴이 기대 경로로 설정되었고, 관리자 로그인과 학생 세션/랭킹 로딩이 정상 복귀했습니다.

회귀 검증에서는 출석 처리, 중복 출석 차단, 상태 조회, 랭킹 계산, 시트 전환, QR 생성이 기존 UX와 동일하게 동작하는지를 함께 확인했습니다.

---

## 7. 보안 관점 정리

관리자 비밀번호는 저장소에 저장하지 않습니다. 운영 절차는 평문 키를 로컬에서 SHA-256으로 변환해 Apps Script `Script Properties.ADMIN_KEY_HASH`에 저장하는 방식입니다.

문서에는 실제 평문 키와 실제 해시값을 기록하지 않고, 아래 플레이스홀더 예시만 유지합니다.

```bash
printf '%s' '<ADMIN_KEY>' | shasum -a 256 | awk '{print $1}'
```

이 원칙을 지키면 문서화 수준이 올라가도 보안 사고 위험은 늘어나지 않습니다.

---

## 8. 운영 교훈

이번 장애 대응에서 얻은 교훈은 명확합니다. 첫째, 공통 통신 계층을 먼저 의심하면 문제 범위를 빠르게 줄일 수 있습니다. 둘째, 사용자에게 보이는 에러 문구 품질은 운영 복구 속도와 직결됩니다. 셋째, 다중 계정 환경은 개발자 로컬보다 실제 운영에서 더 자주 나타나므로, 재현 로그(HAR)를 표준 증거로 삼는 습관이 중요합니다.

결론적으로 이번 수정은 단발성 패치가 아니라, 이후 유사 장애를 더 빠르게 진단할 수 있는 운영 기반을 만든 작업이었습니다.
