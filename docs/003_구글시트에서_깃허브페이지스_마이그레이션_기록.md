# 003 구글시트에서 깃허브페이지스 마이그레이션 기록

## 문서 목적

이 문서는 "기능이 무엇인지"보다 "왜 구조를 바꿨고, 어떤 판단을 거쳐 바뀌었는지"를 기록하기 위해 작성되었습니다. 즉, 나중에 다른 사람이 이 프로젝트를 이어받았을 때 현재 구조를 단순히 외우는 것이 아니라, 당시의 문제와 제약, 그리고 선택의 근거까지 이해하도록 돕는 것이 목표입니다.

---

## 1. 출발점: 단일 GAS 웹앱 구조

초기 시스템은 Google Apps Script가 화면과 로직을 함께 담당하는 전형적인 구조였습니다. `AdminInterface.html`, `StudentInterface.html`, `Index.html`이 Apps Script에서 직접 렌더링되었고, 프런트의 액션은 `google.script.run`을 통해 `Code.gs`를 호출했습니다.

이 구조는 구현 속도가 빠르고 운영 시작이 쉽다는 장점이 있었습니다. Google Sheets를 곧바로 데이터 저장소로 쓸 수 있고, 별도 서버를 두지 않아도 되었기 때문입니다. 그러나 시간이 지나면서 운영 환경이 복잡해지자 문제도 분명해졌습니다.

---

## 2. 문제 인식: 다중 계정 브라우저 환경의 불안정성

운영에서 가장 큰 이슈는 "한 브라우저에 여러 Google 계정이 로그인된 상태"였습니다. 이 조건에서 로그인 컨텍스트가 꼬이거나, 예상과 다른 경로로 요청이 흘러가면서 출석 UX가 불안정해졌습니다. 관리자는 동일한 절차를 안내했는데도 사용자마다 다른 결과가 나오는 상황이 반복되었습니다.

이 시점에서 핵심 질문은 단순했습니다. "문제를 피하려면 사용자 브라우저의 Google 계정 상태에 덜 민감한 구조로 바꿔야 하지 않나?"

---

## 3. 의사결정: 프런트와 백엔드를 분리한다

논의 끝에 구조를 아래처럼 분리하기로 확정했습니다.

- 사용자 화면은 GitHub Pages 정적 페이지에서 제공한다.
- Apps Script는 화면 렌더링을 줄이고, Google Sheets와 통신하는 API 게이트웨이로 집중한다.
- 사용자 입장에서의 기능 흐름은 기존과 동일하게 유지한다.

이 결정의 의미는 "기술 교체"가 아니라 "책임 경계 정리"에 가까웠습니다. 화면 문제는 프런트 배포로, 데이터 로직 문제는 Apps Script 배포로 나누어 다룰 수 있게 되었기 때문입니다.

---

## 4. 구현 과정 타임라인 (2026-02-18)

### 4-1. 마이그레이션 핵심 구현 (`2427c8b`)

첫 단계에서는 `Code.gs`를 API 중심으로 개편하고, 정적 프런트 디렉토리를 신설했습니다. 이때 중요한 포인트는 기존 사용자 흐름을 깨지 않는 것이었습니다. 관리자/학생 페이지를 분리하되, 출석·현황·랭킹·QR 생성 흐름은 이전과 동일한 체감으로 유지했습니다.

Apps Script는 JSONP API 라우터를 제공하도록 정리되었습니다. 초기 핵심 엔드포인트는 `health`, `session`, `attendance`, `status`, `ranking`, `sheets`, `setActiveSheet`, `studentUrl`, `adminUrl`이었고, 이후 운영 고도화 과정에서 Google OAuth 기반 `authGoogle*`, 관리자 목록 `adminUsers*` 액션이 추가되었습니다.

프런트는 `web/admin`, `web/student`, `web/shared`로 분리되었고, 공통 통신 모듈(`api-jsonp.js`)을 통해 `google.script.run` 의존성을 제거했습니다.

### 4-2. 운영 API 연결 (`26e094b`)

구조를 나눈 뒤에는 실제 운영 API URL을 연결해야 했습니다. `web/shared/config.js`의 `API_BASE_URL`이 placeholder 상태면 모든 화면이 실패하므로, Apps Script에서 발급한 최신 `.../exec` URL을 반영했습니다.

이 단계에서 민감정보를 커밋하지 않는 원칙도 명확히 유지했습니다. 현재 인증 기준은 관리자 비밀번호가 아니라 Google OAuth 클라이언트 설정과 관리자 화이트리스트(`_admins`)이며, 운영값은 코드 저장소가 아니라 환경 설정/시트에서 관리합니다.

### 4-3. 이관 후 안정화 (`cdfa27b`)

마이그레이션이 끝난 직후 세션 관련 네트워크 오류가 확인되었고, 별도 이슈 대응으로 이어졌습니다. 이 내용은 `004` 문서에서 상세히 다룹니다.

---

## 5. (a) Apps Script에 실제로 무엇을 적용했는가

운영 기준으로 Apps Script에서 중요한 파일은 `Code.gs`와 `fortune.gs`입니다. `Code.gs`가 API 엔드포인트, 인증, 시트 쓰기/읽기, 세션/랭킹 계산을 담당하고, `fortune.gs`는 출석 완료 시 출력되는 보조 메시지를 제공합니다.

설정은 `Script Properties`에 집중했습니다. `FRONTEND_ADMIN_BASE_URL`, `FRONTEND_STUDENT_BASE_URL`, `GOOGLE_OAUTH_CLIENT_ID`를 통해 프런트 URL과 인증 기준을 외부화했습니다. 이 방식은 코드 수정 없이도 운영값을 바꿀 수 있게 해 주며, 비밀값을 저장소 밖으로 분리하는 보안 효과도 줍니다.

배포는 Web App 방식으로 유지했습니다. 실행 사용자는 소유자 계정, 접근 권한은 `Anyone`로 설정하고, 로직 변경 시에는 항상 새 버전을 재배포해 최신 `exec` URL 유효성을 확인합니다.

---

## 6. (b) GitHub Pages에 무엇을 올렸고 어떻게 배포했는가

GitHub Pages에는 `web/` 하위 정적 자산을 올렸습니다. 관리자 화면(`web/admin`), 학생 화면(`web/student`), 공통 자원(`web/shared`)으로 나누어 운영했습니다.

Secret 관점에서 보면, 커스텀 Secret을 새로 만들지는 않았습니다. 과거 워크플로 이력에서는 배포 도구가 기본 `secrets.GITHUB_TOKEN`만 사용했습니다. 운영 비밀값(관리자 인증 기준)은 GitHub가 아니라 Apps Script 환경 속성으로 유지했습니다.

최종 배포 선택은 `gh-pages` 브랜치 기반 Pages 운영입니다. 즉, 실사용 정적 결과물은 `gh-pages`에서 제공되고, 이 브랜치가 운영 URL과 직접 연결됩니다.

---

## 7. (c) 인증 설정/저장 정책

관리자 인증은 Google OAuth + 관리자 화이트리스트(`_admins`)로 운영합니다. 저장소에는 OAuth 비밀값이나 운영 관리자 목록을 직접 기록하지 않고, Apps Script `Script Properties`(`GOOGLE_OAUTH_CLIENT_ID`)와 스프레드시트 `_admins` 시트에서 관리합니다.

핵심 원칙은 동일합니다. 퍼블릭 저장소에는 비밀값을 남기지 않습니다.

---

## 8. 검증 흐름과 운영 결과

마이그레이션 후 검증은 관리자와 학생 시나리오를 분리해 진행했습니다. 관리자는 인증, 시트 전환, QR 생성, 세션·랭킹 조회를 점검하고, 학생은 시즌 URL 접속, 출석 요청, 출석현황·랭킹 조회를 점검했습니다.

결과적으로 구조 분리 자체는 성공했고, 사용자 경험도 기존과 동일한 흐름으로 유지되었습니다. 이후 발견된 세션 네트워크 오류는 별도 분석과 수정을 통해 안정화했으며, 그 과정은 `004` 문서에서 이어집니다.

---

## 9. 회고

이번 마이그레이션의 핵심 성과는 "문제의 위치를 명확히 분리할 수 있게 된 것"입니다. 이전에는 UI 이슈와 API 이슈가 같은 배포 단위에 묶여 원인 분리가 어려웠지만, 지금은 프런트와 백엔드 책임이 분리되어 장애 분석과 배포 롤백이 훨씬 명확해졌습니다.

운영 관점에서 이 변화는 단순한 코드 개편보다 가치가 큽니다. 동아리 운영 도구는 장기적으로 사람이 바뀌어도 유지되어야 하기 때문에, 구조적 단순성과 책임 분리는 곧 지속가능성으로 이어지기 때문입니다.
