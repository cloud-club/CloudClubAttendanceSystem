# 001 프로젝트 개요 및 운영 가이드

## 이 문서가 다루는 범위

이 문서는 CloudClub 출석 시스템을 실제로 운영하는 사람이 "무엇을 먼저 준비하고, 어떤 순서로 배포하고, 장애 시 어디를 점검해야 하는지"를 한 흐름으로 이해하도록 구성되어 있습니다. 기능 소개보다 운영 맥락을 우선하며, 기술 세부 구현은 `002` 문서에 위임합니다.

---

## 프로젝트의 기본 문제와 해결 방향

CloudClub 출석 시스템의 출발점은 단순했습니다. 동아리 회원 정보를 Google Sheets에 정리하고, 세션별 출석 시간을 같은 시트에 누적 기록하면 운영 비용이 거의 들지 않기 때문입니다. 하지만 실제 운영에서는 브라우저에 여러 Google 계정이 로그인된 상태가 일반적이었고, 그로 인해 GAS HTML 웹앱의 로그인/세션 처리 경로가 흔들리면서 출석 성공률에 영향을 주는 문제가 반복되었습니다.

이 문제를 줄이기 위해 프로젝트는 화면과 데이터 처리의 책임을 분리했습니다. 사용자 화면은 GitHub Pages의 정적 페이지로 고정하고, Apps Script는 시트 입출력과 인증 검증만 담당하는 API 게이트웨이로 축소했습니다. 이렇게 분리하면 사용자 브라우저 경험은 단순해지고, 백엔드는 Google Sheets와의 결합을 유지할 수 있어 운영 연속성을 확보할 수 있습니다.

---

## 현재 운영 구조

현재 운영 구조를 한 문장으로 요약하면 "GitHub Pages가 UI를 담당하고, Apps Script가 Google Sheets API 역할을 담당한다"입니다.

- 프런트엔드 경로
  - 관리자: `https://cloud-club.github.io/CloudClubAttendanceSystem/web/admin/`
  - 학생(기본): `https://cloud-club.github.io/CloudClubAttendanceSystem/web/student/latest/`
- 백엔드 경로
  - Apps Script Web App `.../exec`
- 데이터 저장소
  - Google Sheets (v2: A~L 회원 프로필, M+ 세션 헤더)

운영 시 관리자가 실제로 만지는 것은 크게 세 가지입니다. 첫째는 Google Sheets의 세션 헤더 관리, 둘째는 Apps Script 배포/속성값 관리, 셋째는 GitHub Pages의 정적 파일 배포 상태 점검입니다.

---

## 운영 준비: Google Sheets

출석 시스템의 데이터 기준은 Google Sheets입니다. 회원 기본정보는 고정 영역(A~L열)에 유지하고, 출석 세션은 M열 이후로 계속 오른쪽에 추가합니다. 세션 헤더 형식은 `YYYY-MM-DD-HH:MM` 또는 `YYYY-MM-DD-HH:MM~HH:MM`을 사용해야 하며, 이 형식이 깨지면 세션 인식 로직이 동작하지 않습니다.

실제 운영에서는 다음 원칙을 지키면 오류를 크게 줄일 수 있습니다.

1. 전화번호는 C열(`Phone`) 단일 슈퍼키로 취급합니다. 하이픈/공백이 있어도 내부 비교는 숫자만 남기는 정규화 기준으로 동작합니다.
2. 세션은 "시작 시각 기준 +30분(정시) +60분(지각 마감)" 규칙을 따릅니다.
3. 세션 헤더를 미리 만들 때는 시간대(Asia/Seoul)를 염두에 두고 작성합니다.

### 시트 스키마 v2 표준 헤더

운영 기준 헤더는 아래 12개를 고정 사용합니다.

1. `Name`
2. `Season`
3. `Phone`
4. `Email`
5. `Github ID`
6. `Github Email`
7. `Notion Email`
8. `Discord ID`
9. `Slack Email`
10. `회비 체크`
11. `수료 여부`
12. `운영진 여부`

`Discord ID`가 표준이며, 업로드 파서에서는 `Discor ID` 오타 동의어를 허용합니다.

## 운영 준비: Apps Script

### 필수 파일

Apps Script 프로젝트에서 운영 기준으로 필수인 파일은 `Code.gs`와 `fortune.gs`입니다. `Code.gs`가 API 라우팅, 인증, 시트 기록을 담당하고, `fortune.gs`는 출석 완료 메시지(운세) 생성 보조 역할을 수행합니다.

레거시 HTML(`Index.html`, `StudentInterface.html`, `AdminInterface.html`)은 제거되었고, 현재 UI 렌더링 주체는 GitHub Pages 정적 파일(`web/*`)입니다.

### Script Properties

`Project Settings > Script Properties`에는 최소한 아래 값을 준비해야 합니다.

- `FRONTEND_ADMIN_BASE_URL`
- `FRONTEND_STUDENT_BASE_URL`
- `GOOGLE_OAUTH_CLIENT_ID`

관리자 인증은 Google OAuth 기반입니다. 따라서 `GOOGLE_OAUTH_CLIENT_ID`는 관리자 페이지에서 Google 로그인 버튼 초기화와 서버 ID 토큰 검증(`aud`)에 동시에 사용됩니다.

### 배포 방식

Apps Script는 Web App으로 배포하며, 실행 사용자는 소유자 계정(`Execute as Me`), 접근 권한은 `Anyone`로 설정합니다. 설정을 바꿨거나 코드를 수정했으면 반드시 새 버전을 배포하고 최신 `.../exec` URL을 확인해야 합니다.

Google 로그인 검증은 `UrlFetchApp.fetch`를 사용하므로 `script.external_request` 권한이 반드시 승인되어야 합니다. 로그인 직후 `UrlFetchApp.fetch 권한 없음` 오류가 나오면 계정 권한 문제가 아니라 Web App 런타임 권한 문제입니다. 이 경우 `Deploy > Manage deployments > Edit > Deploy` 재배포 후 권한 승인 팝업을 완료하고, `authGoogleLogin(dummy)` canary 응답이 `AUTH_SERVER_SCOPE_MISSING`이 아닌지 먼저 확인한 뒤 계정별 로그인 테스트를 진행합니다.

## 운영 준비: GitHub Pages

정적 페이지 코드는 `web/` 하위에서 관리합니다. 운영 정책은 `gh-pages` 브랜치 기반 배포이며, 배포가 성공하면 위 운영 URL로 즉시 접근할 수 있습니다.

실무적으로 중요한 포인트는 `web/shared/config.js`의 `API_BASE_URL`입니다. 이 값이 최신 Apps Script `.../exec`와 다르면 관리자/학생 화면이 동시에 실패합니다. 변경 후에는 브라우저 캐시를 비우고(또는 하드 리로드) 실제 호출 경로를 다시 확인해야 합니다.

---

## 관리자 운영 루틴

관리자 관점의 하루 운영 루틴은 대체로 다음 흐름입니다.

먼저 관리자 페이지에 접속해 등록된 Gmail 계정으로 Google 인증을 완료합니다. 이후 현재 시즌을 확인하고(시즌 관리자는 본인 시즌만 접근), 필요하면 데이터를 새로고침합니다. 세션 공지용으로는 학생 `Latest` URL 또는 QR 코드를 생성해 배포합니다. 운영 중에는 세션 상태, 출석 현황, 랭킹 화면을 통해 데이터 반영 여부를 점검합니다.

핵심은 "시트 선택이 곧 운영 대상 시즌"이라는 점입니다. 학생 기본 진입은 항상 `Latest`이며, 과거 시즌 URL(`?season=season_nn`)은 관리자 Google 인증이 있어야만 허용됩니다.

---

## 학생 사용 흐름

학생은 보통 공지된 URL 또는 QR로 접속합니다. 접속 후 현재 세션 활성 여부와 카운트다운이 표시되며, 전화번호 입력 후 출석 요청을 전송합니다. 출석 성공 시 정시/지각 결과와 출석 통계가 제공됩니다. 출석현황 탭에서는 개인 누적 현황과 랭킹을 확인할 수 있습니다.

중복 출석, 미등록 번호, 세션 마감 같은 예외 상황은 서버 기준으로 판정됩니다. 즉, 브라우저 화면이 일시적으로 잘못 보이더라도 최종 결과는 Apps Script + Sheets 상태가 기준입니다.

---

## 운영 점검 체크포인트

운영 중 문제가 발생하면 가장 먼저 아래 세 가지를 순서대로 봅니다.

1. `config.js`의 `API_BASE_URL`이 최신 `.../exec`와 일치하는지
2. Apps Script Script Properties에 필수 키가 모두 존재하는지
3. 네트워크에서 `health`, `session`, `ranking` 호출이 정상 JavaScript 응답을 받는지

이 순서대로 점검하면 프런트 설정 문제와 백엔드 배포 문제를 빠르게 분리할 수 있습니다.

---

## 보안 원칙

이 프로젝트는 퍼블릭 저장소이므로 OAuth 비밀값/운영 계정 정보를 코드에 커밋하지 않습니다. 관리자 허용 목록은 시트 `_admins`에서 관리하고, OAuth 클라이언트 식별자(`GOOGLE_OAUTH_CLIENT_ID`)와 프런트 URL은 Apps Script `Script Properties`에서만 관리합니다.

이 원칙은 편의보다 사고 대응을 우선하는 기준입니다. 운영자 교체나 인수인계 시에도 같은 원칙을 유지해야 장기적으로 안전한 운영이 가능합니다.
