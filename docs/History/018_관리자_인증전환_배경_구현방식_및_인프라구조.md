## 1. 배경
초기 운영 구조는 관리자 진입 시 일반 비밀번호 기반 접근 제어에 의존했습니다. 이 방식은 아래 운영/보안 한계를 반복적으로 만들었습니다.

1. 권한 단위가 약함
- 계정 기반 권한이 아니라 공유 비밀번호 기반이라 사용자 식별과 감사가 어렵습니다.
2. 운영 리스크가 큼
- 비밀번호 변경 시 인수인계 비용이 크고, 누출 시 영향 범위가 넓습니다.
3. 정책 확장성 부족
- `user`, `admin`, `super`처럼 역할별 정책을 안정적으로 분기하기 어렵습니다.

이 문제를 해결하기 위해 관리자 인증 체계를 Google OAuth + 서버 권한 검증 구조로 전환했습니다.

## 2. 채택한 구현 방식
### 2-1. 인증/인가 분리
1. 인증(Authentication)
- Google Identity Services로 ID token 발급
- Apps Script 서버에서 토큰 검증
2. 인가(Authorization)
- `_admins` + 최신 시즌 운영진 데이터 기반 권한 판단
- 고정 Super Admin(`cloudclub2022@gmail.com`) 정책 유지

### 2-2. 단일 정책 진입점
서버는 액션별 접근 레벨을 `ACTION_ACCESS_LEVELS`로 선언하고, `handleApiRequest` 초입에서 공통 가드로 검사합니다.

1. `public`: 로그인 없이 허용되는 조회 계열
2. `admin`: 관리자 인증 필요
3. `super`: 슈퍼 관리자 전용

### 2-3. 운영 안정화 전략
1. 에러 코드를 정책 중심으로 세분화
- 예: `AUTH_SERVER_SCOPE_MISSING`, `AUTH_ADMIN_NOT_REGISTERED`, `AUTH_ADMIN_INACTIVE`
2. 배포 전 canary 게이트 도입
- `authGoogleLogin(dummy)` 결과 코드로 런타임 권한 이상 조기 탐지
3. 문서 중심 복구 체계
- Quick guide(`mission-c`) + SSOT 런북(`019`) 이중 구조

## 3. 문제 해결 과정 요약
이번 전환에서 실제로 큰 이슈는 두 축이었습니다.

1. OAuth Origin 설정 이슈
- 증상: `invalid_client`, `no registered origin`
- 조치: Google Cloud OAuth Client `Authorized JavaScript origins` 정합성 복구
2. Apps Script 런타임 권한 이슈
- 증상: `AUTH_SERVER_SCOPE_MISSING`, `UrlFetchApp.fetch` 권한 오류
- 조치: `__authorizeExternalRequest()` 실행으로 승인 팝업 완료 후 동일 배포 재배포

핵심 교훈은 “계정 권한 문제처럼 보이는 장애가 실제로는 배포 실행 주체/권한 승인 문제일 수 있다”는 점입니다.

## 4. 인프라 구조 (서버리스 + 무료 운영)
### 4-1. Google Cloud
역할:
1. OAuth 2.0 Client 발급 및 Origin 정책 관리
2. Consent Screen 정책 관리(테스트 모드/게시 상태)

운영 포인트:
- 관리자 웹 도메인과 Origin 설정이 정확히 일치해야 로그인 단계가 통과합니다.

### 4-2. GitHub
역할:
1. 프런트 정적 배포(GitHub Pages)
2. 배포 파이프라인(GitHub Actions)
3. 런타임 API URL 주입(`APPS_SCRIPT_WEB_APP_URL` Secret)

운영 포인트:
- Secret 변경만으로는 반영되지 않으며 Pages 재배포가 필수입니다.

### 4-3. Google Apps Script + Google Sheets
역할:
1. API 게이트웨이(`Code.gs`) 및 인증/인가 핵심 로직
2. 운영 데이터 저장소(시즌 시트, `_admins`)

운영 포인트:
- Web App 실행 주체와 권한 승인 상태가 인증 경로 성공 여부를 결정합니다.

## 5. 요청 흐름
### 5-1. 관리자 로그인 경로
1. 관리자 페이지(`/web/admin/`)에서 Google 로그인
2. 프런트가 `idToken`으로 `authGoogleLogin` 호출
3. 서버가 토큰 검증 + 관리자 권한 평가
4. 결과:
- Super/Admin: 세션 발급
- 일반 사용자: `AUTH_ADMIN_NOT_REGISTERED` 등으로 거절

### 5-2. 학생 공개 조회 경로
1. 학생 페이지(`/web/student/`)에서 공개 액션만 호출
2. 서버는 `public` 액션만 허용
3. 관리자 전용 데이터는 접근 차단

## 6. 트레이드오프
| 항목 | 선택 | 장점 | 비용 |
|---|---|---|---|
| 인증 방식 | Google OAuth | 계정 기반 인증, 감사 용이 | 초기 설정 복잡도 증가 |
| 백엔드 | Apps Script | 무료/서버리스/Sheets 연동 용이 | 권한 승인/배포 주체 관리 필요 |
| 배포 구조 | Pages + Secret 주입 | 프런트/백엔드 분리, 운영 유연성 | Secret-재배포 순서 관리 필요 |
| 권한 모델 | `public/admin/super` 선언형 | 정책 가시성/유지보수성 향상 | 문서/체크리스트 동기화 필요 |

## 7. 운영 검증/배포 절차 요약
1. Apps Script 운영 deployment 정합성 확인
2. OAuth Origin/Consent 정합성 확인
3. 필요 시 `__authorizeExternalRequest()` 실행 및 권한 승인
4. 동일 deployment 재배포
5. GitHub Secret 갱신 + Pages 재배포
6. canary 통과 후 계정별 검증

2. 에러 코드 해석 체계 강화
