# 014 시즌업로드 파일정규화 및 파싱 트러블슈팅 런북

> 문서 링크: [docs/History/014_시즌업로드_파일정규화_및_파싱트러블슈팅_런북.md](./014_시즌업로드_파일정규화_및_파싱트러블슈팅_런북.md) | [GitHub](https://github.com/cloud-club/CloudClubAttendanceSystem/blob/gh-pages/docs/History/014_시즌업로드_파일정규화_및_파싱트러블슈팅_런북.md)

## 빠른 흐름도
```mermaid
flowchart LR
  A["문제 징후 확인"] --> B["원인 후보 분리"]
  B --> C["복구 절차 실행"]
  C --> D["검증 게이트 통과"]
  D --> E["증빙/운영기록 저장"]
```


## 1. 배경(어떤 이유로 추가됐는지)
업로드 실패의 상당수는 백엔드 장애가 아니라 입력 파일 형태 불일치에서 발생한다. 대표 증상은 다음과 같다.

- `INF_REQUIRED_LOW_CONF_PHONE`, `INF_REQUIRED_LOW_CONF_EMAIL`
- `INF_MANUAL_CONFIRM_REQUIRED`
- `ROW_n_INVALID_PHONE` 연속 발생
- 최종적으로 `INF_NO_VALID_ROWS`

즉, 파싱 실패는 “파일 자체가 틀렸다”기보다 **현재 추론 규칙이 신뢰 가능한 필수 컬럼을 확정하지 못한 상태**를 의미한다. 이 런북은 운영자가 파일을 빠르게 정규화하고, 반영 가능 상태로 복구하는 절차를 제공한다.

## 2. 사용자 절차(어떻게 사용하는지)
### 2-1. 업로드 전 파일 정규화 체크
1. 필수 컬럼(이름/Season/전화번호/이메일) 존재 여부를 확인한다.
2. 전화번호는 숫자만 유지하고 `010########` 형식으로 통일한다.
3. 이메일은 소문자 기준으로 정리하고 필수 이메일 누락 행을 제거한다.
4. 헤더는 의미가 명확한 텍스트로 고정한다(애매한 별칭/병합셀 금지).
5. 서식보다 값 우선으로 저장한다(표시 형식에 의존하지 않음).

### 2-2. 분석 후 BLOCKER 발생 시 처리
1. `스키마 추론 결과`에서 전화번호/이메일 매핑 컬럼을 수동 지정한다.
2. `현재 매핑 확정` 버튼을 실행한다.
3. 디버그에서 `INF_REQUIRED_LOW_CONF_*` 제거 여부를 확인한다.
4. `ROW_n_INVALID_PHONE`가 남으면 원본 파일의 해당 행 전화번호를 정규화한다.
5. `INF_NO_VALID_ROWS`가 남으면 필수 필드 결측/형식 오류 행을 제거 후 재분석한다.

### 2-3. 업데이트 모드에서 파싱은 통과했지만 Diff가 과도한 경우
1. 즉시 최종 반영을 누르지 않는다.
2. `Diff 보기=변경만`으로 전환해 실제 의도 변경만 남는지 확인한다.
3. 여전히 과도하면 업데이트를 중단하고 `create` 경로로 우회한다.

## 3. 설계 의도(왜 이렇게 했는지)
파싱 단계의 본질은 “데이터 반영”이 아니라 “반영 가능성 평가”다.  
이 단계에서 보수적으로 차단하는 것은 실패한 반영보다 안전하다.

- 신뢰도 Low 차단: 잘못된 대량 반영 방지
- 수동 매핑 확정: 운영자가 최종 책임 지점 확보
- 유효 행 0건 차단: 빈/오염 데이터 반영 방지

이 런북은 추론 정확도를 강제로 높이기보다, 운영자가 빠르게 정상 입력 상태를 만들도록 하는 실행 절차에 초점을 둔다.

## 4. API/데이터 영향
| 항목 | 관측 포인트 | 운영 영향 |
|---|---|---|
| 파일 분석/추론 | 필수 필드 confidence | Low면 반영 차단 |
| 미리보기 상태 | `VALID_INSERT` 행 수 | 0건이면 반영 불가 |
| 업로드 세션 | begin/chunk/finalize 흐름 | 분석 품질이 낮으면 begin 이전 단계에서 중단 |
| update Diff | 비교 노이즈 가능성 | 파싱 통과와 update 신뢰성은 별개로 판단 필요 |

## 6. 운영상 주의점
- 전화번호 열이 사람이 보기엔 맞아도, 숫자 외 문자가 섞이면 `INVALID_PHONE`로 처리된다.
- 필수 필드 confidence가 0.00이면 매핑 후보를 거의 찾지 못한 상태다. 이때는 바로 반영하지 않는다.
- 수동 매핑 확정은 “분석 결과를 신뢰한다”는 운영자 승인 단계다.
- 분석 통과 후에도 update Diff는 별도 검증이 필요하다(형태 차이 노이즈 가능).

## 7. 검증 시나리오
1. 표준 템플릿 파일에서 분석 직후 BLOCKER 없이 `VALID_INSERT`가 생성되는지 확인한다.
2. 전화번호 형식이 혼재된 파일에서 `ROW_n_INVALID_PHONE`가 재현되는지 확인한다.
3. 수동 매핑 확정 후 confidence 관련 BLOCKER가 해소되는지 확인한다.
4. 동일 데이터(표현만 다름) 파일에서 update Diff의 과다 감지 여부를 점검하고 정책에 따라 create 우회가 가능한지 확인한다.

## 8. 실제 운영 사례(실패 예시/대응 예시)
### 사례 1. 전화번호 필드 신뢰도 0.00 + 유효 행 0건
실패 상황: 분석 단계에서 필수 필드 BLOCKER와 `INF_NO_VALID_ROWS`가 동시에 발생했다.  
원인: 전화번호 열 추론 실패 + 원본 값 형식 불일치.  
대응: 전화번호 컬럼 수동 매핑 후 `현재 매핑 확정` 실행, 원본 전화번호를 숫자형으로 정규화한 뒤 재분석.  
재발 방지: 업로드 전 표준 템플릿에 맞춘 사전 정규화 체크리스트를 운영 루틴에 포함.

### 사례 2. 분석은 통과했지만 update 결과가 과도하게 달라 보임
실패 상황: 일부 변경만 의도했으나 미리보기에서 삭제 후보/변경이 과다 표시됐다.  
원인: 동일 의미 데이터의 표현 차이가 현재 비교 규칙에서 변경으로 계산됨.  
대응: 업데이트 반영 중단 후 create 우회, 파일 표준화 후 재시도.  
재발 방지: update 모드는 표준 파일에서만 사용하고, 대규모 반영은 create 우선 정책 유지.

## 9. 남은 리스크/차기 개선 포인트
- 파싱 성공과 update 정확도는 분리된 문제다. 현재는 파싱 복구 절차 중심으로 운영 리스크를 낮춘다.
- 파일 형태 다양성이 계속 증가하면 운영자 수동 보정 비용이 커질 수 있다.
- 차기에는 canonical 정규화 규칙과 필드별 동등성 판단을 강화해, 표현 차이로 인한 노이즈를 줄여야 한다(`015` 참조).
