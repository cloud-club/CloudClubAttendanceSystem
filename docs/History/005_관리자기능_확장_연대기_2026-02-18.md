## 1. 배경(어떤 이유로 추가됐는지)
2026-02-18의 관리자 페이지 확장은 단순 UI 개선이 아니라 운영 리스크를 줄이기 위한 구조 개선 작업이었다. 실제 운영에서 가장 큰 문제는 다음 세 가지였다.

- 시즌/시트 명명 규칙이 불안정해서 운영자가 잘못된 시즌에 기록할 위험이 컸다.
- `variable` 시트가 레거시 구조와 신규 구조가 섞이면서 계산 기준이 흔들렸다.
- 배포 체계가 분산되어 있어 Apps Script 재배포와 Pages 반영 타이밍이 어긋나면 기능이 정상이어도 장애처럼 보였다.

특히 이번 확장은 “기능 부족”보다 “운영 불확실성”을 해소하기 위한 대응이었다는 점이 중요하다. 기존에도 출석은 가능했지만, 운영자는 같은 작업을 해도 시점과 순서에 따라 서로 다른 결과를 받는 상황을 반복해서 겪었다. 예를 들어 같은 시즌을 보고 있다고 생각했는데 실제로는 다른 시트에 쓰고 있었고, 변수 값을 바꿨는데 일부 계산만 반영되는 일이 있었다. 이런 상태에서는 기능이 많아져도 신뢰가 떨어지기 때문에, 먼저 기준 체계를 고정하고 나서 기능을 쌓는 접근이 필요했다.

이 문서는 `004` 이후의 변경을 시간 순으로 복기해, 왜 기능이 추가되었고 왜 안정화 커밋이 반복되었는지 운영 맥락을 포함해 정리한다.

## 2. 사용자 절차(어떻게 사용하는지)
이 문서는 기능 매뉴얼이 아니라 “결정 흐름 문서”다. 읽는 순서는 다음을 권장한다.

1. 본 문서에서 시점별 변경 축을 먼저 파악한다.
2. 기능별 상세는 `006~011` 문서로 이동한다.
3. 실제 운영 점검은 `012` 체크리스트를 기준으로 수행한다.

문서를 이렇게 읽도록 설계한 이유는 “결과”보다 “의사결정 배경”을 먼저 이해해야 이후 변경을 안전하게 이어갈 수 있기 때문이다. 운영 현장에서 가장 자주 발생하는 질문은 “왜 이 버튼이 생겼는가?”보다 “왜 이 규칙을 강제하는가?”에 가깝다. 따라서 본 문서는 기능 설명서가 아니라 변경의 맥락과 실패-수정 루프를 기록하는 근거 문서로 사용한다.

실무에서는 장애/질문이 생겼을 때 “언제 추가된 기능인지”를 먼저 찾고, 해당 커밋과 상세 문서를 연결해서 확인하면 재현 속도가 빨라진다.

## 3. 설계 의도(왜 이렇게 했는지)
이번 확장의 설계 의도는 “기능 추가”보다 “운영 통제 가능성 확보”에 있었다.

- 기능 확장은 `v2 -> v3.1 -> v3.2 -> v3.3 -> v3.5`로 단계화했다.
- 각 단계마다 불안정 포인트를 즉시 `fix` 커밋으로 봉합했다.
- 시트/프런트/배포를 동시에 만지는 변경은 반드시 런북(`011`)으로 환원했다.

이 접근은 의도적으로 보수적이다. 한 번에 크게 바꾸면 단기적으로는 빠르지만, 운영자가 체감하는 실패 지점이 어디인지 추적하기 어렵다. 반대로 단계형 배포와 즉시 안정화 커밋을 병행하면 “무엇을 바꿨을 때 무엇이 나아졌는지”를 추적할 수 있다. 이번 연대기에서 `feat`와 `fix`가 촘촘히 교차하는 이유가 바로 여기에 있다.

즉, 관리자 페이지는 편의 기능을 늘리는 방향이 아니라, 운영자가 실수해도 복구 가능한 구조를 만드는 방향으로 고도화됐다.

## 6. 운영상 주의점
- Apps Script를 먼저 배포하고 Pages를 나중에 배포해야 “프런트는 새 URL, 서버는 구버전” 불일치를 줄일 수 있다.
- `variable` 중복행은 조회 시 자동 삭제하지 않는다. 정리는 `variablesNormalize`/템플릿 복구 액션으로만 수행한다.
- `APPS_SCRIPT_WEB_APP_URL`은 Secret 변경만으로 반영되지 않는다. 반드시 Pages 재배포가 필요하다.

운영자가 기억해야 할 핵심은 “같은 변경이라도 반영 순서가 품질을 결정한다”는 점이다. 코드가 맞아도 배포 순서가 뒤집히면 장애처럼 보이는 현상이 다시 발생한다. 이 문서군(005~012)은 단순 기능 목록이 아니라, 이런 순서 의존 리스크를 줄이기 위한 실행 순서를 함께 담고 있다.

## 7. 검증 시나리오
1. 관리자 페이지 로드 후 API 버전/URL 표시가 최신인지 확인한다.
2. 변수 탭 진입 5회 반복 시 `variable` 행 수가 증가하지 않는지 확인한다.
3. 출석 순위가 `출석횟수 > 평균 오프셋 > 이름` 기준으로 고정됐는지 확인한다.
4. 일정 캘린더에서 동일 날짜 신규 저장 시 중복 차단이 동작하는지 확인한다.
5. 유고 덮어쓰기 시 2단계 확인이 강제되는지 확인한다.

## 8. 실제 운영 사례(실패 예시/대응 예시)
### 사례 1. 기능은 배포됐는데 운영 화면은 예전 동작을 보인 경우
실패 상황: `Code.gs`를 최신 버전으로 배포했는데 관리자 화면에서는 이전 정책(예: 메타 `-` 표기, 구 정렬 기준)이 계속 보였다.  
원인: Pages 산출물은 구버전 `env.js`를 참조하고 있었고, 브라우저 캐시까지 겹쳐 새 API를 보지 못했다.  
대응: `apiInfo`로 실제 연결 버전을 먼저 확인하고, Secret 갱신 후 workflow 재배포와 강력 새로고침을 순서대로 수행했다.  
재발 방지: “Apps Script 배포 -> Secret 갱신 -> Pages 재배포 -> apiInfo 확인” 순서를 운영 체크리스트에 고정했다.

### 사례 2. 변수 정책 변경 직후 일부 탭만 계산이 이상했던 경우
실패 상황: variable 값을 수정한 뒤 수료 판정은 정상인데 출석 카운트다운이 비정상적으로 표시됐다.  
원인: 중복 키와 오염값(`0:00`)이 남아 조회 경로마다 다른 값이 선택됐다.  
대응: `variablesNormalize`로 중복/오염 데이터를 정리하고, `variablesResetTemplate(preserve)`로 메타를 복구했다.  
재발 방지: 운영자 직접 시트 복붙을 금지하고, 변수 변경은 관리자 탭 `value` 편집만 사용하도록 운영 규정을 변경했다.

## 9. 남은 리스크/차기 개선 포인트
- 관리자 탭 기능이 빠르게 늘어 단일 JS 파일 복잡도가 상승했다. 모듈 분리가 필요하다.
- 배포 검증 자동화는 강화됐지만, 운영자가 브라우저 캐시를 비우지 않으면 구버전 화면을 볼 수 있다.
- 변수 정책은 안정화됐지만 시즌별 변수 스코프 분리 요구가 생길 가능성이 높다.
