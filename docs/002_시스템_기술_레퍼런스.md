# 002 시스템 기술 레퍼런스

## 문서 성격

이 문서는 함수 목록을 단순 나열하는 사전이 아니라, 현재 시스템이 어떤 책임 분리와 데이터 흐름 위에서 동작하는지를 설명하는 기술 해설서입니다. 실제 구현 파일을 기준으로 설명하며, 운영 중 디버깅할 때 어떤 레이어를 먼저 봐야 하는지까지 함께 다룹니다.

---

## 1. 아키텍처 요약

현재 시스템은 세 계층으로 나뉩니다.

첫째 계층은 GitHub Pages 정적 프런트입니다. 관리자와 학생 화면은 각각 `web/admin`, `web/student`에서 독립적으로 로드되며, 공통 통신/설정은 `web/shared`에 모여 있습니다.

둘째 계층은 Apps Script API 게이트웨이입니다. `Code.gs`는 화면을 렌더링하기보다 JSONP API 라우팅에 집중합니다. 이 계층이 인증, 시트 접근, 출석 기록, 상태/랭킹 계산을 담당합니다.

셋째 계층은 Google Sheets 데이터 계층입니다. 실데이터는 시트에 저장되며, 서버는 시트 헤더/행 데이터를 읽어 세션과 출석 상태를 계산합니다.

이 구조의 핵심은 "화면 배포와 데이터 처리 배포를 분리"했다는 점입니다. UI 수정은 GitHub Pages 배포로 처리하고, 시트 로직 수정은 Apps Script 버전 배포로 처리합니다.

---

## 2. 백엔드(`Code.gs`) 설계

### 2-1. 진입점과 라우팅

`doGet(e)`는 요청 파라미터를 보고 두 경로 중 하나를 선택합니다. `api` 파라미터가 있으면 API 라우터(`handleApiRequest`)로 들어가고, 그렇지 않으면 프런트 URL 리디렉션 또는 레거시 HTML fallback을 수행합니다.

`handleApiRequest`는 액션 이름을 기준으로 분기하며, 공통 응답 포맷은 `apiSuccess`/`apiError`로 통일됩니다. 현재 주요 액션은 `health`, `session`, `attendance`, `status`, `ranking`, `sheets`, `setActiveSheet`, `verifyAdminKey`, `studentUrl`, `adminUrl`입니다.

### 2-2. JSONP 응답 전략

브라우저 환경 제약과 호환성을 고려해 `callback(payload)` 형태의 JSONP 응답을 반환합니다. `validateCallback`으로 콜백 이름을 검증해 임의 코드 실행 위험을 줄이고, `createJavascriptOutput`으로 MIME 타입을 JavaScript로 명시합니다.

### 2-3. 관리자 인증

관리자 인증은 `verifyAdminKey`에서 처리합니다. 사용자 입력 평문은 SHA-256으로 변환되고, `Script Properties.ADMIN_KEY_HASH`와 비교됩니다. 일치하면 `issueAdminToken`으로 단기 토큰을 발급하고, 이후 민감 API(`setActiveSheet`)는 `verifyAdminToken`으로 토큰을 검증합니다.

핵심 포인트는 인증 기준이 코드가 아니라 환경 설정에 있다는 점입니다. 즉, 저장소 유출과 운영 비밀값 관리가 분리됩니다.

### 2-4. 시트 선택 및 시즌 분리

관리자 모드는 `activeSheet` 속성을 기준으로 시트를 선택합니다. 학생 모드는 URL 쿼리의 `season`으로 직접 시트를 지정합니다. 이 분리 덕분에 관리자는 운영 대상 시즌을 바꿀 수 있고, 학생은 안내받은 시즌으로만 접근합니다.

### 2-5. 세션 계산 로직

세션 헤더는 `YYYY-MM-DD-HH:MM` 형식을 따르며, 서버는 이를 파싱해 `startTime`, `onTimeDeadline(+30m)`, `lateDeadline(+60m)`를 계산합니다. 현재 시각이 이 윈도우 안에 있으면 활성 세션으로 간주합니다.

이 계산은 서버 기준으로 수행되므로, 클라이언트 시계 오차나 조작이 있어도 최종 판정은 안정적으로 유지됩니다.

### 2-6. 출석 기록과 판정

`markAttendanceInSheet`는 입력 검증, 세션 유효성, 중복 출석, 사용자 매칭을 순차 처리한 뒤 시트에 타임스탬프를 기록합니다. 동시에 정시/지각을 판정해 셀 배경색을 다르게 적용합니다.

- 정시 색상: `#6d9eeb`
- 지각 색상: `#f6b26b`

이 단계에서 통계(출석 횟수/출석률)도 함께 계산해 프런트에 즉시 반환합니다.

### 2-7. 상태/랭킹 계산

상태 조회는 세션별 출석 타입(`on_time`, `late`, `absent`, `future`)을 계산해 상세 리스트를 반환합니다. 랭킹은 완료된 세션만 대상으로 출석률을 계산하고, 동률일 경우 평균 체크인 시간으로 정렬합니다.

즉, 학생이 보는 랭킹은 단순 출석 횟수가 아니라 "출석률 + 도착 시간" 복합 기준으로 산출됩니다.

## 3. 프런트엔드 설계

### 3-1. 공통 계층(`web/shared`)

`config.js`는 API 엔드포인트와 통신 옵션을 제공합니다. `api-jsonp.js`는 실제 요청을 생성하고, 타임아웃/오류 처리/콜백 정리를 담당합니다. 여기서 통신 정책을 한 번 바꾸면 관리자와 학생 화면 모두에 동일하게 반영됩니다.

최근 장애 대응 이후 `api-jsonp.js`는 `crossOrigin='anonymous'`, `referrerPolicy='no-referrer'`를 기본 적용하며, 오류 객체에 진단 정보를 포함합니다. 이로써 네트워크 장애의 원인 추적성이 개선되었습니다.

### 3-2. 관리자 화면(`web/admin`)

관리자 화면은 로그인 모달에서 관리자 키를 입력받아 토큰을 확보한 뒤, 시트 목록/시트 전환/QR 생성/세션·랭킹·출석 처리 기능을 제공합니다. 시트 전환은 단순 UI 상태 변경이 아니라 백엔드의 `activeSheet` 변경 API를 통해 반영됩니다.

관리자 화면의 중요한 역할은 "현재 운영 시즌을 제어"하는 것입니다. 따라서 시트 전환과 QR 생성은 한 흐름으로 관리되는 것이 안전합니다.

### 3-3. 학생 화면(`web/student`)

학생 화면은 URL 쿼리의 `season`을 받아 해당 시즌 세션 정보를 읽고, 출석/현황/랭킹을 제공합니다. 세션이 비활성이면 출석 버튼이 자동 비활성화되고, 활성 시에는 카운트다운과 함께 입력이 가능해집니다.

학생 화면은 최대한 단순한 입력 경험을 제공하되, 실제 검증은 모두 서버에서 수행하기 때문에 데이터 무결성이 유지됩니다.

---

## 4. 데이터 흐름

실제 요청 흐름은 다음과 같습니다.

1. 브라우저가 `CloudClubApi.call(action, params)`를 호출한다.
2. `api-jsonp.js`가 callback 이름을 생성해 `<script src=".../exec?...&callback=...">`를 삽입한다.
3. Apps Script `handleApiRequest`가 액션별 로직을 수행하고 JSONP를 반환한다.
4. 브라우저 콜백이 실행되며 UI가 갱신된다.

장애 분석 시에는 이 흐름에서 어느 단계가 끊겼는지 확인하면 된다. 예를 들어 script tag 자체가 실패하면 ORB/CSP/리다이렉트 계층을 먼저 의심하고, callback은 왔지만 `ok:false`이면 서버 로직이나 입력값 검증 계층을 점검한다.

---

## 5. 배포와 설정 연계

시스템은 두 배포 단위를 갖습니다.

- GitHub Pages 배포: 정적 파일(`web/*`) 반영
- Apps Script 배포: API 로직(`Code.gs`) 반영

운영에서 가장 흔한 실수는 한쪽만 반영하는 경우입니다. 예를 들어 `API_BASE_URL`이 이전 배포 URL을 가리키면 프런트는 정상 배포되어도 API 호출이 실패합니다. 반대로 Apps Script만 수정하고 프런트 설정을 유지하면 새 기능이 사용자 화면에 반영되지 않을 수 있습니다.

따라서 변경 후에는 "프런트 URL, API URL, Script Properties" 세 가지를 한 세트로 점검해야 합니다.

---

## 6. 보안 및 운영 안정성 원칙

이 프로젝트는 퍼블릭 저장소 운영을 전제로 하므로, 관리자 평문 키와 실제 해시값은 코드/문서에 남기지 않습니다. 인증 비밀값은 Apps Script 환경 속성에서만 관리하고, 프런트/커밋에는 절차와 인터페이스만 남깁니다.

또한 장애 대응 시에는 사용자 메시지와 운영자 진단 메시지를 분리해 관리합니다. 사용자에게는 행동 가능한 안내를 제공하고, 콘솔/로그에는 민감값이 마스킹된 디버그 정보를 남겨 재현성과 보안을 동시에 확보합니다.
