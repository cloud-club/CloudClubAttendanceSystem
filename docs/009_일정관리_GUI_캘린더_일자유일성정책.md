# 009 일정관리 GUI 캘린더, 일자 유일성 정책

## 1. 배경(어떤 이유로 추가됐는지)
기존 일정 관리는 회차 키 중심 입력 폼에 의존해 운영자가 일정을 직관적으로 보기 어려웠다. 특히 다음 문제가 있었다.

- 신규 일정과 기존 일정 수정의 구분이 약해 오입력 가능성 증가
- 월 단위로 일정 밀집도를 보기 어려움
- 동일 날짜에 중복 회차가 생겨 출석 계산이 꼬일 위험 존재

운영 맥락에서 일정은 단순 데이터 입력이 아니라 출석 계산의 기준점이다. 일정이 잘못 들어가면 출석 오픈/지각/마감 시간이 모두 어긋나고, 이후 수동 승인·수료 계산까지 연쇄적으로 영향을 받는다. 따라서 일정 관리 UX는 보기 편한 수준을 넘어 “실수해도 안전한 입력 흐름”을 보장해야 했다.

이를 해결하기 위해 기존 일정폼은 유지하고, 하단에 월간 캘린더 블록을 추가했다.

## 2. 사용자 절차(어떻게 사용하는지)
1. `일정 관리` 탭 하단 `캘린더 보기` 카드에서 월을 이동한다.
2. 날짜 셀의 `+` 버튼을 누른다.
3. 해당 날짜 일정이 없으면 `새 회차 추가`, 있으면 `일정 수정` 모달로 열린다.
4. 시작시간/종료시간을 설정하고 저장한다.
5. 삭제가 필요하면 모달의 삭제 버튼을 눌러 기존 강제확인 플로우로 진행한다.

기존 상단 일정폼도 계속 사용할 수 있고, 캘린더와 동일 저장 API를 공유한다.

즉, 운영자는 기존 익숙한 방식(상단 폼)을 계속 사용할 수 있으면서, 월간 관점이 필요할 때는 캘린더에서 빠르게 추가/수정할 수 있다. 두 UI가 같은 저장 로직을 쓰기 때문에 입력 경로가 달라도 결과 일관성이 유지된다.

## 3. 설계 의도(왜 이렇게 했는지)
### 기존 운영 습관 보존
기존 폼을 삭제하지 않고 캘린더를 추가한 이유는 운영자 학습 비용을 낮추기 위해서다.

### 데이터 무결성 우선
UI가 편해져도 데이터 무결성이 깨지면 의미가 없기 때문에 “한 날짜 1회차”를 서버에서 강제했다.

### 충돌 가시화
중복 데이터가 기존에 이미 있는 경우 자동 삭제하지 않고, 충돌 경고를 띄워 운영자가 의도적으로 정리하게 했다.

이 설계는 자동 복구보다 운영 판단을 우선한다. 중복 회차를 시스템이 임의로 삭제하면 단기적으로는 깔끔해 보여도, 기존 출석 데이터와 정합성이 깨질 수 있다. 그래서 충돌을 숨기지 않고 노출한 뒤 운영자가 확인하고 정리하도록 정책을 정했다.

## 4. API/데이터 영향
| API | 변경 내용 | 영향 |
|---|---|---|
| `scheduleList` | `dateKey`, `startHhmm`, `dateConflicts` 필드 확장 | 프런트가 타임존 파싱 의존 없이 안정 렌더 |
| `scheduleSave` | 동일 날짜 중복 시 `SCHEDULE_DATE_DUPLICATE` 반환 | 잘못된 중복 일정 저장 차단 |
| `scheduleDelete` | 기존 강제 삭제 정책 유지 | 출석 기록이 있는 회차 삭제 리스크 완화 |

데이터 정책:

- Script Timezone(KST) 기준으로 `dateKey(YYYY-MM-DD)` 산출
- 동일 `dateKey`에 서로 다른 `sessionKey`는 저장 금지

## 6. 운영상 주의점
- 동일 날짜에 의도적으로 2개 회차를 두는 운영은 현재 정책에서 허용되지 않는다.
- 기존 데이터에 이미 중복 날짜가 있다면 먼저 충돌 정리를 해야 신규 저장이 된다.
- 일정 삭제는 출석 기록과 직접 연결되므로 강제삭제 판단을 신중히 해야 한다.

## 7. 검증 시나리오
1. 캘린더가 일요일 시작 7열로 렌더되는지 확인한다.
2. 오늘 날짜 강조/선택 상태가 정상인지 확인한다.
3. 일정 없는 날짜 `+` 클릭 시 `새 회차 추가` 모드로 열리는지 확인한다.
4. 일정 있는 날짜 `+` 클릭 시 `일정 수정` 모드로 열리는지 확인한다.
5. 동일 날짜로 새 회차 저장 시 `SCHEDULE_DATE_DUPLICATE`가 반환되는지 확인한다.
6. 저장/삭제 후 일정목록, 캘린더, 출석 세션 상태가 함께 갱신되는지 확인한다.

## 8. 실제 운영 사례(실패 예시/대응 예시)
### 사례 1. 같은 날짜에 회차가 2개 생겨 출석 판정이 어긋난 경우
실패 상황: 동일 날짜에 다른 시작시각 회차가 중복 생성되어 학생마다 활성 세션이 다르게 보였다.  
원인: 저장 단계에서 날짜 유일성 검증이 없어서 운영자가 모달/폼에서 각각 생성한 데이터가 공존했다.  
대응: `scheduleSave`에서 날짜 충돌 시 `SCHEDULE_DATE_DUPLICATE`를 반환하도록 서버 검증을 추가하고, 캘린더 상단에 충돌 경고를 노출했다.  
재발 방지: 중복 데이터는 자동 삭제하지 않고 운영자가 직접 정리하도록 하여, 기존 출석 데이터 손실을 막았다.

### 사례 2. 신규 일정인데 버튼 문구가 “수정”으로 보인 경우
실패 상황: 운영자가 신규 입력인지 기존 수정인지 즉시 구분하지 못해 잘못 저장했다.  
원인: 폼 상태와 버튼 라벨이 고정돼 있어 사용자 맥락을 반영하지 못했다.  
대응: 신규 회차는 `일정 추가`, 기존 회차는 `일정 수정`으로 문구를 분기하고 토스트 메시지도 동일하게 분기했다.  
재발 방지: 캘린더 모달/상단 폼 모두 동일 저장 헬퍼를 사용해 상태 판정 기준을 한 곳으로 통일했다.

## 9. 남은 리스크/차기 개선 포인트
- 월간 뷰만 제공하므로 회차가 많은 시즌은 주간/리스트 하이브리드 뷰가 추가로 필요할 수 있다.
- 날짜 유일성 정책이 고정되어 있어 특별 행사(같은 날 2회) 요구가 생기면 정책 옵션화가 필요하다.
